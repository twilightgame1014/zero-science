# HD-2Dグラフィック仕様・Claude/Muse連携契約

更新日: 2026-11-06  
担当: Muse（描画原本）／Claude（ゲーム側との統合）／GPT（仕様・レビュー）

## 1. 目標表現

3Dの地形・建築物に2Dスプライトの主人公を組み合わせるHD-2D表現。段丘、崖の岩肌、川、滝、草木、石段・石垣、遠景を活用する。柔らかい光、影、ブルーム、チルトシフト等は端末負荷に配慮して使用する。

参照資料: `references/hd2d-tilesets/`、`assets/lab-stages*/`。研究室背景は原始的な作業場から現代的施設までの4段階のアセットがある。

## 2. ファイルと責任の境界

| パス | 役割と扱い |
| --- | --- |
| `threejs-hd2d-graphics/` | Museの受け渡し用原本。API変更はここを更新する |
| `src/graphics/` | ゲームビルドが使う統合用コピー。Claudeが取り込み・型チェック |
| `src/graphics-entry.ts` | ゲームと描画の起動ブリッジ（Claude） |

描画の変更内容を統合する際は、原本→統合用コピーの同期を追跡し、どの版を採用したかPRに記録する。同期したことが確認できない場合は「統合済み」としない。

## 3. 状態の所有者

**ゲーム状態の唯一の正本はClaude側。** 座標、所持品、採取状態、建物、衝突判定、技術開放、セーブ、時間の進行はゲームロジックが管理し、Muse側は受信した状態を描画する。

描画内部では、補間座標やアニメーション位相など表示専用の状態だけを保持してよい。レンダラー側から所持品、採取結果、建築の成否、研究進捗を変更しない。

## 4. 連携API（既存仕様）

原則として以下の**公開API**を介してゲームが描画へ情報を渡す。

- `initializeGraphics(...)`、`disposeGraphics()`
- `setPlayerVisualState(...)`、`setPlayerSpriteSheet(...)`
- `setWorldVisualState(...)`、`setCameraTarget(...)`
- `updateResourceVisual(...)`
- `addStructureVisual(...)`、`removeStructureVisual(...)`
- `playVisualEffect(...)`
- `resizeGraphics(...)`

厳密なシグネチャ・対応型・実装有無は必ず `src/graphics/types.ts` と `src/graphics/index.ts` で確認する。ここに列挙した名前が将来も必ず存在することは保証しない。

座標系: 右手系・Y軸上・地面XZ平面、ゲーム座標1単位=描画1単位が既定。現行ゲームでは `terrainHeight` による地表高さを基準にする。

主人公スプライトの既存仕様は4列×4行（下・左・右・上の4方向行）。差し替え時は実際のスプライトの規格と見た目を確認する。

## 5. 現状の統合リスク（改善候補）

`src/game/ui.js` は描画ループの停止・再開に `gfx.stopLoop` / `gfx.startLoop` を参照している。既存のClaude向け指示では `pauseGraphics` / `resumeGraphics` の正式API追加がMuseへの未解決依頼。**正式APIが追加・統合されるまでは未対応扱い**にする。

`src/game/ui.js` の資源表示マッピングでは `water`、`oil` を利用している。専用表現はMuseに要確認。既存デモや仮表示があることを本番対応済みと混同しない。

未解決の描画要望:
- 洞窟・鉱山・火山・海岸・油田の地形表現
- 川を渡るための橋と歩行可能・不可能領域の整合
- 水位に応じた地形色の確認
- 水車、蒸気機関、精留塔、掘削やぐら等の追加モデル
- 端末性能による描画品質・ポストエフェクトの最適化

これらは既存 `CLAUDE.md` に記載された依頼内容を移したものであり、対応済みを意味しない。

## 6. 変更・統合のプロトコル

1. Museは描画用ブランチに変更を置く（モデル・素材・公開API・型・受け渡し文書）。
2. 公開APIの追加・変更・削除がある場合は変更前後の型、呼び出し例、互換性をPRに明記する。
3. Claudeはゲーム側の統合ブランチで `src/graphics/` を原本から同期する。元の変更履歴を失わないようにする。
4. 実ゲームの採取・移動・建築・画面遷移・スマホ操作を通して確認する。
5. `npm run typecheck`・`npm run build`・`npm test` を実行し、必要に応じて `npm run e2e` と実描画の手動確認を行う。
6. 採用版を記録し、オーナーがレビューしてから`main`へマージする。

原本と統合コピーを両方別々に手修正してドリフトを増やさない。できる限り一方向の同期を守る。

## 7. 受け入れ確認項目

- キャラクターが正しい位置・向き・動作で表示される
- 資源の採取済み表示がゲームデータと一致する
- 建物の追加・削除が状態と一致する
- PC・スマホで入力と描画が成立する
- 描画エラー時にゲーム進行を破壊しない
- セーブ・ロード後に表示が再現される
- エフェクト・影・背景が性能を過度に損なわない

グラフィックの最終的な美術判断と妥協点はオーナーが決定する。

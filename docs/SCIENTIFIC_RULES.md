# 科学データと実験判定の品質基準

更新日: 2026-11-06  
適用範囲: 天然資源・化学物質・材料・製品・実験・教育的説明

## 1. 最上位原則

1. **実在する科学的な知識を優先する。** 実在物質と架空のゲーム演出を混同しない。
2. **検証できる範囲で反応を実装する。** 未登録の組み合わせをAIの推測で「反応成功」にしない。
3. **自然資源から到達できることを確認する。** 中間体・道具・設備の依存関係を考慮する。
4. **科学的正確性とゲームとしての操作性を両立する。** 単純化した部分を実在の厳密な製法と誤認させない。
5. **危険な製造工程は抽象化する。** 危険性の高い化学物質、医薬品等の実行可能な製造条件・手順は記載しない。

## 2. データ種別の区分

| データ種別 | 扱い方 |
| --- | --- |
| 単体・化合物 | 明確な化学的同定、可能な範囲で組成・物性・出典 |
| 鉱石・土・海水など | 混合物。含有物の種類やばらつきは現実の傾向に沿う |
| 合金・高分子・複合材料 | 単一化合物と同じ扱いをしない。組成・性能・加工履歴を区別 |
| 製品・装置 | 物質ではなく部品や工程の組み合わせ。化学式を無理につけない |
| 医薬品・バイオ製品 | 成分／製剤／評価・品質管理を別段階とする。安全性・有効性を製造成功だけで断定しない |

物質の**発見**（自然から採集・観察）、**同定**（分析で何か分かる）、**製造**（操作で得る）は概念上別。ゲームUIや図鑑でも区別できる設計を優先する。

## 3. 現行反応データの仕様

現行コードの科学データは `src/game/data.js`、反応照合は `src/game/engine.js` に存在する。

- `procs`: 実験ID、操作 `op`、設備 `at`、原料 `inp`、生成物 `out`、説明 `why`、補助道具 `tools`、周囲の空気 `air`、目安温度 `temp` など。
- `crafts`: 工作ID、結果アイテム、材料、道具、作業設備、説明 `how`。
- `items`: 永続ID、種別タグ、元素の種類、教育的説明など。

現在の数量は主に**ゲーム用の単位**。工業的な物質収支や厳密なモル比を保証するものではない。

現行テストの元素保存チェックは、主に**原料と空気にない元素が生成物に現れないこと**を検査する方式。元素ごとの原子数や質量を厳密に保存する完全な化学量論バリデータとは別物である。後者は将来の品質強化項目。

## 4. 反応追加のレビュー手順

1. 対象を「化学反応」「物理的分離」「加工・組立」「生物的変換」のどれかに分類する。
2. 物質IDと科学的な同定を確認し、混合物や製品に不適切な化学式を付けない。
3. 原料、主な生成物、副生成物、設備、操作、技術的依存関係を定義する。
4. 危険性を確認し、必要なら温度・比率・製造条件などを抽象化する。
5. 元素・物質収支を検討する。現行の簡略チェックで足りない部分は注意書きと検証TODOを残す。
6. 出典と教育用説明を用意する。未確認の数値は捏造せず空欄または未検証とする。
7. 既存の技術ネットワークから到達できることをシミュレーションで確認する。
8. テスト、図鑑表示、セーブ互換性を確認する。

## 5. 科学データの信頼度

採用情報は次のように分類して管理することを推奨する。

- **A: 出典確認済み** — 信頼できる一次情報、査読論文、公的データベース等で確認した内容。
- **B: 教育的な簡略化** — 科学的原理に沿うが数量や手順をゲーム向けに抽象化した内容。
- **C: 検証待ち** — 未確認の記述・数値。ゲーム内で断定せず、公開前に検証する。

出典候補: PubChem、ChEBI、Open Reaction Database、適切な公的・学術資料。外部ソースを使う場合は、**ライセンス・再配布条件・更新日**も管理する。特定DBに収録されたことはゲーム内での製造可能性を意味しない。

### 将来の推奨メタデータ（未実装）

- `sourceRefs`: 参考資料と識別子
- `reviewStatus`: A/B/Cの品質区分
- `checkedAt`: 確認日
- `simulationNotes`: 簡略化の範囲
- `hazardClass`: ゲーム表示用の危険性分類
- `routeStatus`: 反応経路検証済み／未検証／未実装

これらは**拡張提案**であり、現在のゲームデータに存在するものとして扱わない。

## 6. 実験結果の処理とバランス

- 失敗時にアイテムが増える、同時に複数回消費されるなどの不整合を防ぐ。
- 未登録プロセスでは、現行仕様どおり原料を消費しない。
- 採集時の希少アイテム抽選と、化学反応の成功可否は別問題。未確認の物質が乱数で突然生まれる仕組みにしない。
- 温度、圧力、純度、収率などの詳細モデルは後続の研究課題。実装完了まで説明やUIで精密シミュレータを名乗らない。
- 学習向け説明は、小学生にも読みやすい `kid` と詳しい `more`、実験の `why`、工作の `how` を維持する。

## 7. 安全と教育

医薬品、危険な薬品、有毒ガス、危険な反応などは**概念上の研究・品質評価・安全管理**としてモデル化する。実施可能な薬品製造の操作条件、配合、収量を最適化する手順や、危険を伴う実験手順を説明しない。

ゲーム内の仮想実験が現実の自宅実験の安全性を保証するような文言を避ける。医療上の判断に使える資料として宣伝しない。

## 8. テスト方針

最低限、既存の `npm test` と `tests/sim.mjs` の到達可能性テストを通す。追加データの変更では、対象反応の再現テストとゲーム状態の回帰テストを増やす。

現行の「元素の種類を確認するテスト」と、将来の「元素数・物質収支を検証するテスト」を混同しない。

# AI共同開発ルール（開発憲章）

更新日: 2026-11-06  
対象: 『ゼロからの科学 〜石と水と木から〜』  
承認者: プロジェクトオーナー（ユーザー）

## 1. この文書の目的

GPT・Claude・Museが同じGitHubリポジトリを参照し、責任範囲の重複、仕様の食い違い、成果物の上書きを防ぐ。AI間の会話・メモリは自動同期されないため、**GitHub上の文書とコードを共有情報の正本**とする。

この文書はチームの運用ルールであり、GitHubのブランチ保護設定を自動的に有効化するものではない。

## 2. 役割と決裁権

| 役割 | 主担当 | 作業と権限 |
| --- | --- | --- |
| プロジェクトオーナー | ユーザー | 方向性・仕様の最終決定、リリース・マージ承認、優先順位 |
| ゲームディレクター | GPT | 要件整理、ゲーム／科学システム仕様、受入基準、コード・設計レビュー、Claude/Muse向け指示書 |
| リードエンジニア | Claude | ゲームデータ・ロジック・UI・保存・ビルド・テストの実装、描画モジュールの統合 |
| グラフィックエンジニア | Muse | HD-2D表現、Three.js描画モジュール、アセット、キャラクター・環境・VFX・描画性能 |

**役割は担当範囲の目安であり、AIが互いの作業を自動実行することを意味しない。** 担当外の変更が必要なときは、変更理由と影響を文書化してオーナーに確認する。

### ファイルの責任範囲

- Claudeの主担当: `src/game/`、`src/template.html`、`src/graphics-entry.ts`、`scripts/`、`tests/`、`package.json`、ゲーム側に最適化したアセットの配置。
- Museの主担当: `threejs-hd2d-graphics/`（描画モジュール原本）、`references/`、`assets/lab-stages*/` および描画アセットの原本。
- `src/graphics/` は**Muse原本から取り込まれた統合用コピー**。Claudeが統合するが、Museの描画内部ロジックは原則として独断改変しない。
- GPT: `docs/` 内の共有仕様を策定・更新し、変更提案をレビュー可能な形で提示する。ゲーム本体のコード変更は明示依頼がある場合に限定する。
- `CLAUDE.md` はClaudeの実装作業ルール。共通ルールに矛盾させず、既存のテスト・保守規則を維持する。

## 3. 参照する正本と優先順位

実装前に該当文書を読み、次の優先順位を守る。

1. オーナーが明示的に承認した最新の個別要件・変更決定
2. `docs/TEAM_RULES.md`（役割・変更管理）
3. `docs/GAME_DESIGN.md`（ゲーム仕様）と `docs/SCIENTIFIC_RULES.md`（科学の正確性）
4. `docs/GRAPHICS_SPEC.md`（表現・描画の責任境界）
5. `docs/DEVELOPMENT_ROADMAP.md`（予定・進捗）と `docs/CHANGELOG.md`（変更記録）
6. `CLAUDE.md`（Claude固有の実装ルール）

**実装済みの事実**はコードとテストの結果で確認する。文書に書かれた将来構想を「実装済み」と扱わない。描画APIの正確な型は `src/graphics/types.ts`、既存の統合手順は `docs/handoff/INTEGRATION.md` を正本として参照する。上記の優先順位は型定義や動作事実を上書きするものではない。

矛盾を見つけた場合は、静かに一方へ寄せて実装せず、差異・影響・推奨案を記載して解消する。

## 4. 標準ワークフロー

1. **依頼**: オーナーが目的・重視する体験を共有する。
2. **設計**: GPTが機能の範囲、対象ファイル、依存関係、受入基準、危険な変更、未確定点を整理する。
3. **承認**: 大きな仕様変更はオーナーが決定する。承認されていないアイデアは「提案」と明記する。
4. **実装**: ClaudeとMuseが各自の担当ブランチで作業する。描画APIを変更する場合は必ず双方で合意する。
5. **統合**: Claudeが描画の変更をゲーム本体へ接続し、コード・テスト・セーブ互換性を確認する。
6. **レビュー**: GPTが仕様との差、科学的な妥当性、UI、テスト範囲をレビューする。
7. **採用**: オーナーの確認後にPull Requestを`main`へマージし、必要な仕様・履歴を更新する。

### 推奨ブランチ名

- ゲーム本体: `feature/game-短い内容`
- グラフィック: `feature/graphics-短い内容`
- 仕様書・開発体制: `docs/短い内容`
- バグ修正: `fix/短い内容`

`main` は原則として安定版。**開発変更を直接pushせずPR経由**にする。これは運用ルールなので、技術的に強制するにはGitHubのRulesets/branch protectionを別途設定する必要がある。

## 5. タスクと引き継ぎの共通フォーマット

次の項目をGitHub Issue、PR本文、または仕様書に記載する。

- タイトル／目的：プレイヤー体験として何を改善するか
- 状態：提案／承認済み／実装中／レビュー中／完了／保留
- 主担当：Claude または Muse。仕様策定はGPT
- 変更対象：具体的なファイル・API・データ
- 入出力契約：イベント、識別子、型、座標、セーブ形式
- 受入基準：実際に何ができれば完成か
- テスト：最低限実行するテストと手動確認箇所
- 互換性：既存セーブ・スマホ・PC・他モジュールへの影響
- 保留事項：未解決の仕様・依存・リスク

不明点は「未確定」として記録し、勝手に既成事実化しない。

## 6. 変更・レビュー・品質ゲート

PRを出す前に、対象に応じて以下を確認する。

- `npm test`：科学データ説明、元素の種類の整合性、物質の到達可能性、エンジン挙動などの既存テスト。
- `npm run typecheck`：描画モジュールの型検査。
- `npm run build`：配布用HTMLのビルド。
- `npm run e2e`：ブラウザの結合テスト（実行環境を準備できる場合）。偽描画モジュールを使うため、実描画の外観評価は別途必要。
- PC・スマートフォンでの手動動作検証。バージョンや確認端末をPRへ記録する。
- セーブスキーマ変更時の旧セーブ移行テスト。
- 学習コンテンツ追加時の科学的根拠と安全性確認。

**テストを実行していなければ「未実行」と書く。** ソースを読めたことと、実機で正常動作したことを混同しない。

## 7. 統合境界と禁止事項

- 描画モジュールは表示専用。採取・衝突・建築可否・所有物・研究進捗を決定しない。
- ゲーム側は描画モジュールの内部メソッドに依存せず、公開APIだけを利用する方向へ改善する。
- 既存のアイテムIDとセーブ構造を無断変更しない。変更時は移行方法を設計する。
- 出典のない新物質・架空の化学反応を、現実の科学的事実として扱わない。
- 危険な物質や医薬品の実行可能な製造手順をゲーム内に提供しない。安全な抽象化と教育的説明に留める。
- アセットの原本とビルド用の圧縮・加工コピーを混同しない。
- API・素材・依存・ライセンスの変更はPR本文に明記する。
- オーナーの承認なく第三者への公開、課金、破壊的な変更、公開設定変更を行わない。

## 8. 定例的な作業の始め方

- GPT: `TEAM_RULES` → 対象仕様 → 最新コード／Issue／PRを読んで設計とレビューを行う。
- Claude: `CLAUDE.md` → `TEAM_RULES` → 対象仕様とAPI定義を読み、担当ブランチで実装する。
- Muse: `TEAM_RULES` → `GRAPHICS_SPEC` → `docs/handoff/INTEGRATION.md` → `src/graphics/types.ts` を読み、描画原本側で作業する。
- 作業完了時には、実装内容、未対応事項、テスト結果、依頼したい相手側の作業を引き継ぐ。

## 9. 運用開始について

本ルールは共有文書として追加する**提案**であり、PRが`main`にマージされ、オーナーが採用して初めて正式な運用基準になる。
